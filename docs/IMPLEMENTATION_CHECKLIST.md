# Task Tracker v1.2 Implementation Checklist

**Review date:** 23 November 2026

**Baseline:** TaskTracker Product Requirements Document v1.2 and TaskTracker Software Requirements Specification v1.2, both drafts dated 19 November 2026.
**Database decision:** PostgreSQL is the runtime database. Current API routes use normalized PostgreSQL tables; the converted JSONB source is preserved as `app_records_legacy`, and Google Sheets remains unchanged. This persistence cutover does not imply that all v1.2 product requirements are complete.

> **Historical snapshot:** The status tables and repository findings below were reviewed before the later unified-Task, project/backlog, and authorization work. Statements that PostgreSQL, rich-text descriptions, task attachments, task types, Reject/Reopen, or project detail/backlog are absent are stale. Use [PENDING_IMPLEMENTATION_TASKS.md](./PENDING_IMPLEMENTATION_TASKS.md) for the 24 November 2026 revalidation and current remaining-work status; retain this file as the v1.2 requirements baseline, not a current code inventory.

## 1. Review method and status meanings

This review covers all 150 numbered PRD requirements and all 201 numbered SRS functional requirements, 4 data-integrity requirements, and 20 defined non-functional requirements. Requirement rows below group IDs only when they share a feature area and implementation status; each ID is enumerated in the ID/priority column and inherits the row's description, status, evidence, remaining work, and test needs.

- **IMPLEMENTED** — the stated behavior is present and supported by relevant automated test evidence.
- **PARTIALLY IMPLEMENTED** — related code exists, but one or more material v1.2 behaviors, fields, controls, or safeguards are missing.
- **NOT IMPLEMENTED** — no relevant implementation was found.
- **NEEDS VERIFICATION** — code exists, but the behavior cannot be confirmed from available automated tests or runtime evidence.

Priority abbreviations: PRD `Must`, `Should`, `Could`; SRS `M` (Must), `S` (Should), `C` (Could). Where the source document does not assign a priority, this is stated. Status is based on repository evidence, not the presence of a screen alone. Files are relative to the repository root. This checklist tracks v1.2 requirements and does not claim full v1.2 completion.

## 2. Repository baseline

### Stack and persistence

- Frontend: React 18, React Router, and a mixture of Create React App and Vite configuration. The active application entry is `frontend/src/index.js` → `frontend/src/App.js`.
- Backend: Node.js and Express. Routes are mounted in `backend/server.js`.
- PostgreSQL is configured with `DATABASE_URL` or discrete connection settings. Versioned migrations define the normalized schema; the app store maps the existing API contract to users, projects, work items, sprints, releases, templates, notifications, and issue child tables.
- Four users, one project, and two issues were converted from `app_records` using a transactional, validated migration. The old rows are archived in `app_records_legacy`; memberships were reconciled using the union of both legacy relationship arrays. The source spreadsheet was not modified.
- `backend/services/sheetsStore.js` remains for legacy format definitions and read-only migration extraction. Runtime storage is `backend/services/postgresStore.js`.

### Active frontend and backend surfaces

- `frontend/src/App.js` mounts login, registration, dashboard, issues, tasks, profile, sprints, releases, admin users, and admin projects. It does not mount most v1.2 routes. Duplicate `.js`/`.jsx` implementations exist; the active imports in `App.js` use `.js` for several pages.
- `backend/server.js` mounts auth, users, projects, issues, templates, tasks, notifications, sprints, and releases. There is no central resource policy middleware.
- Current backend route files: `backend/routes/auth.js`, `users.js`, `projects.js`, `issues.js`, `tasks.js`, `notifications.js`, `sprints.js`, `releases.js`, and `templates.js`.
- The backend suite has 13 passing tests covering configuration, the SheetsStore legacy format, password policy, migration parsing, and normalized PostgreSQL store CRUD/concurrency. Permission-matrix, frontend component, and end-to-end coverage remain absent.

### Current features to preserve

The codebase contains working implementations worth retaining and regression-testing as the v1.2 work is added:

- Registration/login, JWT authentication, bcrypt password hashing, strong-password checks, configurable registration, and basic profile updates (`backend/routes/auth.js`, `backend/middleware/auth.js`, `backend/utils/passwordPolicy.js`, `frontend/src/context/AuthContext.js`).
- Issue CRUD, search/filter, summary/export, comments, time logs, activity, and issue attachment upload (`backend/routes/issues.js`, `frontend/src/pages/Issues.js`, `frontend/src/components/IssueModal.jsx`).
- Task CRUD, basic filters, summary/export (`backend/routes/tasks.js`, `frontend/src/pages/Tasks.js`).
- Project CRUD and owner/member-based project listing (`backend/routes/projects.js`, `frontend/src/pages/AdminProjects.js`).
- Admin/member user management; basic sprint/release/template CRUD APIs; notification persistence and read marking.
- Login branding currently references `/zcs_logo.png` from `frontend/src/pages/Login.js`.

These are source-level findings, not end-to-end verification. Preserve their existing API paths and response shapes unless a documented, versioned compatibility decision permits a change. Retest each feature against the PostgreSQL repository and new authorization rules.

## 10. Findings: defects, security gaps, and database gaps

- **Database mismatch/blocker:** no PostgreSQL code, schema, migration, or `DATABASE_URL` configuration exists; the server startup requires Sheets. This is the first implementation dependency under the confirmed PostgreSQL decision.
- **Authorization/data exposure:** issue/task and several other resource routes rely mainly on authentication and do not consistently scope reads, aggregates, writes, or deletes to a visible project/action. `GET /api/users` returns hydrated user records to any authenticated user. See `backend/routes/issues.js`, `backend/routes/tasks.js`, `backend/routes/users.js`, `backend/routes/sprints.js`, `backend/routes/releases.js`, and `backend/routes/templates.js`.
- **Project update authorization:** `PUT /api/projects/:id` has no owner/admin/policy check; project creation also accepts caller-supplied owner/members. See `backend/routes/projects.js`.
- **Public attachment serving:** `backend/server.js` exposes the uploads directory with `express.static`. `backend/routes/issues.js` writes uploaded data to local disk without the SRS MIME/extension/scanning rules and without an authenticated download endpoint.
- **Input validation gaps:** some endpoints validate required fields but there is no shared schema validation/rejection of unknown fields across routes; task, sprint, release, template and issue updates accept allowlisted fields with limited type/range validation.
- **User/profile privilege gaps:** profile update accepts `assignedProjects`; admin user routes accept arbitrary role strings and do not implement Super Admin protections or the role enum.
- **Persistence correctness:** SheetsStore has no relational foreign keys, SQL indexes, database transactions or multi-instance coordination. Issue numbering based on current list count can conflict under concurrency. Its write queue is process-local.
- **Session hardening:** frontend bearer token is stored in localStorage (`frontend/src/context/AuthContext.js`, `frontend/src/api.js`); no refresh/token-version mechanism or CSRF/session-cookie approach is implemented. Helmet, CORS allowlisting and rate limits exist, but required account-level failed-login throttling is absent.
- **Frontend duplication and orphan pages:** `.js`/`.jsx` alternatives exist; `Projects.jsx`, `Reports.jsx`, and several other pages are not mounted by `frontend/src/App.js`. Presence alone is not delivery.
- **Operational gaps:** only `/api/health` was found; no readiness probe, structured request logs/request IDs, metrics, documented backups or tested restore procedure were found.

## 11. Recommended implementation order

1. **Phase 0 — PostgreSQL and safety foundation:** design the PostgreSQL schema and repository/migrations; plan a verified Sheets-to-PostgreSQL data migration; establish compatibility and rollback; implement central authorization, five roles, departments, audit, input validation, secure attachment storage/download, and permission tests.
2. **Phase 1 — Project hub:** implement project and membership policy, scoped dashboard APIs, milestones, completion/health calculations, project detail, and My Work/workload navigation.
3. **Phase 2 — Work management:** implement backlog and conversion; enrich tasks/issues with type, dates, rich text and safe attachments; add blocker/rejection workflows; expose unified Work while preserving existing CRUD, comments, time logs, activity, filters and exports.
4. **Phase 3 — Collaboration:** expand in-app notifications; add durable email outbox, scheduling, recipient rules and retries; mount notifications, sprints, releases and templates in the project-aware UI.
5. **Phase 4 — Insights and operational acceptance:** add completion analytics/reports as approved; meet accessibility/performance/observability requirements; implement backup/restore and CI coverage; run end-to-end, security, migration, load and regression suites.

**Preservation gate:** before replacing each existing route or page, capture its current request/response behavior and add regression tests. Migrate users, projects, issues, tasks, comments, attachments, activity, notifications, sprints, releases, and templates with reconciliation reports; do not remove the Sheets path or source data until PostgreSQL migration and rollback are verified.
